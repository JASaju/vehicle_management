# Vehicle Management System Documentation

## 1. Purpose and scope

This Laravel application manages a vehicle fleet, drivers, maintenance, fuel usage, parking occupancy, users,
and operational reports. It also exposes a public landing page and optional token-protected parking sensor and
plate-recognition APIs.

The running project has been reported as Laravel 13.43.0. `composer.json` requires PHP 8.3 or later and
constrains Laravel to `^13.17`, Livewire to `^4.0`, and PowerGrid to `^7.0`.

## 2. Application components

| Component | Responsibility |
|---|---|
| Blade, Livewire, and PowerGrid | Authenticated screens, module forms, searchable tables, and exports |
| Laravel web routes and controllers | Authentication, fleet/parking operations, reports, and public SEO endpoints |
| Eloquent models | Domain data, relationships, and casts |
| Configured SQL database | Users, vehicles, drivers, maintenance, fuel, and parking state |
| Parking sensor API | Receives occupancy changes from a configured sensor gateway |
| Plate-recognition API | Receives a plate result from a separate OCR/camera service |
| Security JSON log channel | Writes selected security events to daily local log files |
| Host SIEM collector | Optional external ingestion; it is not configured by this application |

`database/migrations` is the authoritative schema evolution source. The MySQL DDL-only reference is
`database/vehicle_management_schema.sql`; see [Database Schema](database-schema.md).

## 3. User roles and access

- The public landing page, `/robots.txt`, and `/sitemap.xml` do not require authentication.
- Operational screens require an authenticated, active account. Public registration is disabled.
- `staff` users can access fleet operations and reports. `admin` users can additionally manage users and open
  the read-only **Security Logs** page.
- Inactive users are logged out on their next authenticated request. Login attempts are limited to five per
  minute per email/IP combination.
- The first administrator is provisioned from deployment configuration when seeding. Use a unique password;
  never store deployment secrets in source control.

## 4. Main business flows

### Fleet and costs

Users maintain vehicle types, vehicles, drivers, maintenance jobs, and fuel entries. Fuel totals are computed
server-side as liters multiplied by price per liter. Fuel and maintenance odometer readings can raise a
vehicle's odometer but cannot lower it. An in-progress maintenance job moves an eligible vehicle to
`in_maintenance`; when no job remains in progress, that status returns to `active`.

### Parking

The Parking map shows configured slots and current stays. Manual park/release and sensor events create or close
`parking_records`. A record with `released_at = NULL` is the current stay. A sensor can create an occupied
record before a vehicle is identified; in that case `vehicle_id` remains `NULL` and the detected plate can be
assigned later. Transactions and row locks protect the app's park/release/identify workflows.

### Sensor and OCR integrations

The API routes are:

| Method and path | Sender | Purpose |
|---|---|---|
| `POST /api/parking/sensor` | Arduino/ESP-01 gateway | Set a configured slot's occupied/free state |
| `POST /api/parking/plate` | Separate OCR/camera service | Attach a recognized plate to a slot event |

The endpoints use separate bearer tokens, configured slot codes, request validation, and database transactions.
Both tokens must be at least 32 characters and the configured slot list must contain exactly ten entries. The
slot codes must resolve unambiguously in the database. Keep tokens out of firmware repositories, browser code,
and logs.

The sample Arduino firmware uses plain HTTP and is for a trusted private network only. Do not expose it or its
bearer token to the public internet; use a trusted TLS-terminating gateway and network restrictions for a
production device deployment. The hardware example is not a VAPT-tested deployment.

### Reports and SEO

PDF reports are generated by mPDF. The public landing page has canonical/social metadata; the sitemap advertises
only the landing page. Login and authenticated pages are marked `noindex`; robots directives are not access
controls.

## 5. Security logging and SIEM

Authentication outcomes, logout, authorization denials, user administration, and profile updates are written
as JSON to daily files at `storage/logs/security-YYYY-MM-DD.log` (30-day retention by default). Event fields
are intentionally limited; passwords, tokens, request bodies, query strings, and login identifiers are not
included.

Admins can read the latest normalized events at `/security-logs`. The view is read-only and bounded; it does not
show raw log context. The app does **not** forward events to a SIEM vendor. Configure a host-side collector to
ingest the JSON log files, then restrict and monitor access to both the log directory and the collector.

No VAPT findings/report were supplied. This document describes the current implementation; it is not a VAPT
assessment and does not claim that finding-specific remediation has been completed.

## 6. Installation and operational notes

For the full install flow and supported package versions, follow the project [README](../README.md). In brief:

1. Install PHP 8.3+, Composer, and Node.js; install PHP and JavaScript dependencies.
2. Set application URL, database connection, bootstrap administrator credentials, and any optional integration
   tokens in the deployment environment.
3. Back up an existing database, then run `php artisan migrate`. Seed only when the sample fleet data is wanted.
4. Build frontend assets and run the app behind the deployment's HTTPS-capable web server.
5. Schedule database backups and configure log rotation/collection appropriate to the deployment.

The checked-in `database/vehicle_management.sql` is a data dump that contains `DROP TABLE` statements and
sample rows; do not import it into a database whose contents must be preserved. The user-supplied SQL dump is
also older than the sensor migration: its parking schema does not include the current sensor fields and makes
`parking_records.vehicle_id` non-null. Use Laravel migrations for upgrades. A schema-only MySQL reference with
no sample records is provided separately, but migrations remain the installation source of truth.
